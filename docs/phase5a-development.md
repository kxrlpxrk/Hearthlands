# Phase 5A: Selective district development

## Controls and safety

Select a district in **Districts**, then press **Develop district**. Fill available space is the default and never removes anything. Set an additional-building target (1–60), preferred compatible catalogue types, density, layout, seed and permission to propose roads. With no preferred types selected, the district's catalogue mix is used; if one compatible type cannot fit, another is tried without relaxing constraints.

**Regenerate selected buildings** shows an individual checklist. Only unlocked buildings whose whole footprints lie inside the eligible district may be checked. Membership alone is not permission: straddling buildings, hidden/locked neighbour claims, and locked objects remain protected. The replacement count is the number explicitly checked. A second confirmation checkbox in the preview names the actual removals. When a replacement cannot fit, its approved original stays in place; there is never an empty hole left just to satisfy the requested count.

**Improve connections** proposes access spurs to existing district roads for existing buildings; it does not alter buildings or reroute infrastructure. New bridges, clearing woodland, terraforming and moving walls are outside this phase. A district without any accessible existing road or bridge bank needs a manually drawn road inside its boundary first. It is never connected by modifying a neighbouring district.

District locking disables development. Object locks are independent: unlocking a district does not unlock any building or road. All old buildings and infrastructure are protected regardless of ID or provenance. An old `generated-…` ID is never treated as consent. Original roads retain their IDs, points, widths, surfaces, names and locks. Existing terrain, district boundaries, settlement ID and planning metadata are retained.

## Proposal behaviour

Generation runs in a cancellable worker against the current document. It does not regenerate terrain or use the whole-map building generator destructively. The draft is separate from the document and is not autosaved, snapshotted or exported as a completed change. Green shows new buildings, red shows approved original footprints to remove, gold shows proposed paths, and cyan outlines the affected district. The comparison shows additions/removals, old/new total building counts and fitted/requested counts. Expand **Review constraints and changes** for individual objects and rejected-candidate reasons.

In preview mode, one-finger drag pans and two-finger gestures pan/zoom without editing. Cancel terminates generation or drops the draft. **Development settings** reopens the bottom sheet. Accept applies the combined building/path proposal. If capacity is insufficient, **Accept smaller proposal** explicitly accepts the fitted subset. Empty proposals cannot be accepted. Nothing is deleted or resized to make the requested count fit.

Acceptance validates the proposal against the unchanged source and verifies its deterministic output. Any intervening manual edit makes the draft stale and requires a fresh preview. Current committed edits are flushed, an **Automatic backup before district development · [district name]** restore point is created, and then the proposal becomes one history command and is saved. A failed backup prevents application. Double acceptance is blocked. Editing is guarded during backup so an asynchronous write cannot apply over a newer in-memory edit. Normal autosave consistency and cross-tab revision protection remain in force; storage errors remain visible and JSON export can back up in-memory work.

## Rules and compatibility

New footprints and the full width of new access paths must remain inside selected district cells, excluding every neighbouring district's claims. Buildings use catalogue footprints, quarter-turn rotations, edited shared terrain queries, slope/height limits, resource access and clearance. Sparse / balanced / dense reserve 2 / 1 / ½ tile around other buildings; integer placement can round this up. Existing entrances, logical and rendered infrastructure footprints and gathering/harbour working grounds are reserved. Water services require nearby water reachable across usable land; sawmills require reachable woodland. Roads use bounded four-neighbour navigation, avoid footprints and defenses, use existing gates, and preserve terrain and bridge banks. Visual smoothing is checked separately; a new spur uses straight segments if smoothing would cross a district edge or defense.

Optional `provenance` on **new** buildings and roads is version 1 with source, district ID, seed, proposal ID and (for replacements) original building ID. It is informational, never authorization. Document version 3 and the IndexedDB schema remain intact. Old v1/v2/v3 imports need no destructive migration. Full JSON, autosave, snapshots, undo/redo and the existing complete PNG renderer retain accepted development. Manual edits do not erase provenance, and provenance never makes those edits expendable.

The same complete input document, district, normalized settings and seed produce identical proposals and IDs. Candidate scans, terrain checks and navigation operate on district cells; original infrastructure is indexed once per proposal. Search counts are bounded, and cancellation remains available while the worker runs.

## Physical iPhone acceptance

1. In **Projects**, duplicate Ravenfjord and open the copy. Use a Viking River / Contextual / seed 1847 / 96 × 96 / 35-building reference map; explicitly detect and confirm districts if necessary. Keep a JSON backup. Never perform the test on your only copy.
2. Tap **Districts**, select an unlocked residential district and press **Develop district**. Leave Fill selected, target **5**, balanced density, contextual layout and seed 1847. Check only **House / cottage** under preferred types and leave **Propose new access roads** enabled.
3. Press **Generate development preview**. Inspect five green cottages, gold paths, the cyan boundary and 35 → 40 counts. Use one finger to pan and two to pinch. Existing buildings must not move. Cancel once and verify no buildings or history entries were added; generate again and verify the same locations.
4. Tap **Accept development**. Wait for **Saved on this device**. In **Projects → Restore points**, verify the automatic pre-development backup. Original building IDs/positions and original roads must remain unchanged.
5. Select a different residential or compatible district, press **Develop district**, and choose **Regenerate selected buildings**. Check exactly two eligible unlocked buildings. Choose compatible preferred types. Generate, expand the review, and verify only those two originals are red. Unselected and locked buildings must stay unchanged.
6. Confirm the explicit replacement checkbox, then accept. If only a smaller valid subset fits, review which originals are retained before accepting the smaller proposal. Do not expect a full replacement count when boundaries, roads or terrain prevent it.
7. Select the harbour district and lock it. Verify **Develop district** is disabled. Individual building/road locks must remain as they were. Unlocking the district must not unlock its contents.
8. Close the sheet. Undo the harbour lock first if it was the most recent edit, then Undo the accepted development once. The whole replacement, including new paths, must revert together. Redo it and wait for Saved. Repeat for the earlier fill if desired.
9. Close and reopen Safari on the same device/site. Open the copied project and inspect all accepted edits and the automatic backups. The original Ravenfjord project must remain unchanged. Restore a backup only through the existing confirmation flow, which also backs up the current document.
10. Export JSON, import it as a separate project, and verify building identities, provenance, roads, terrain and districts. Prepare/download a **2048 px** PNG and inspect the whole map, including new buildings and access paths. On Safari use Downloads / Files, or Share → Save to Files if the image opens. Choose 1024 px if image memory is limited.

## Limits

Development does not expand district boundaries, resize the map, clear vegetation, sculpt terrain, add bridges, move defenses, regenerate a whole settlement, or infer ownership of old generated objects. Very small/irregular districts, unavailable resources, no existing in-district road, imported overlapping claims and protected open spaces can reduce capacity to zero. Existing disconnected road networks are preserved; a new spur connects to usable existing local infrastructure rather than repairing the entire settlement network. Density is a spacing preference, not permission to violate safety. Previews are ephemeral; accept or cancel before leaving/reloading the site. Physical Safari requires the device test above; Chromium touch emulation alone is not physical-iPhone verification.
